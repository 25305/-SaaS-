# 配额与计量说明（模块 C · API Key / 模块 D · 配额与计量）

> 定位：把模型调用变成**可管控、可核算**的商业行为。本文是模块 C/D 的口径说明书，也是评审入口。
> 配套证据：`backend/tests/test_quota.py`、`backend/tests/reports/quota_report.md`。
> 表结构定稿后字段语义不再变更——成员 D 的看板与账单导出都依赖它。

## 1. 配额维度

**双维度、按自然月**（FR-D1）：

| 维度 | 字段 | 口径 |
|---|---|---|
| Token 总量 | `tenants.quota_monthly_tokens` / `api_key.quota_monthly_tokens` | `prompt_tokens + completion_tokens` 的当月累计 |
| 请求次数 | `tenants.quota_monthly_requests` / `api_key.quota_monthly_requests` | 当月**消耗配额**的请求数（见 §2 计数口径） |

- 两个维度**可分别设上限**，任一维度触顶即视为超限。
- 字段为 `NULL` 表示该维度**不限制**。
- **解析优先级：Key 级 > 租户级**（FR-C4）。Key 级字段为 `NULL` 时继承租户级配置：

```python
def effective_quota(key, tenant):
    tokens = key.quota_monthly_tokens if key is not None and key.quota_monthly_tokens is not None \
        else tenant.quota_monthly_tokens
    requests = key.quota_monthly_requests if key is not None and key.quota_monthly_requests is not None \
        else tenant.quota_monthly_requests
    return tokens, requests
```

> 判断用 `is not None` 而**不是**真值判断：`0` 是合法的"一律拒绝"配置，用 `if key.quota_...` 会把 `0` 误判成"未配置"而回退到租户配额，造成越权放行。

**限额独立性的关键差别**：租户口径与 Key 口径的**统计范围不同**。

- **租户口径**：读聚合表 `usage_summary` 的当月所有分桶求和（快，见 §3）。
- **Key 口径**：`usage_summary` 没有 Key 维度，因此按 `usage_record.key_id` 过滤当月流水求和（FR-C4 要求单 Key 配额独立，若 Key 也用租户合计值就会互相影响）。

因此 `test_key_quota_isolated_within_tenant` 的构造是：租户配额不限，仅把 Key1 配额设为 1；Key1 超额返回 429，同租户 Key2 仍 200。

## 2. Token 统计口径与请求计数口径

### 2.1 Token：只用模型返回的 `usage`，**绝不估算**（FR-D2）

```python
usage = resp.usage
if usage is None:
    logger.error("llm_usage_missing", extra={"request_id": ctx.request_id, "model": model})
    prompt_tokens = completion_tokens = 0        # 宁可记 0 并告警,也不猜
else:
    prompt_tokens, completion_tokens = usage.prompt_tokens, usage.completion_tokens
```

- **不允许 tiktoken 之类的估算**——估算是验收红线（任务书 §七）。
- 每次调用都写 `llm_call_completed` 日志，并带 `usage_source: "response.usage"`：验收时 `grep usage_source` 即可证明数据来源，而不是"看代码相信"。
- 该日志同时记录 `model_provider`，未配置真实上游时其值为 `local-simulation`（本地模拟模型），如实标注而不伪装成真实供应商（与项目"健康探针不谎报 up"的既有哲学一致）。

### 2.2 请求计数：只统计"消耗配额"的状态

| `status` | 计入 Token | 计入请求次数 | 说明 |
|---|---|---|---|
| `success` | ✅ | ✅ | 正常模型调用 |
| `error` | ❌（记 0） | ✅ | 上游异常/超时：请求确实发生，Token 无从获取 |
| `quota_rejected` | ❌（记 0） | **❌** | 预检拦截，**尚未调用模型**；只作审计痕迹 |
| `cache_hit=1` | ❌（记 0） | ✅ | 缓存命中：请求照记，Token 不重复计 |

**为什么 `quota_rejected` 不计入请求次数**：若把拒绝也计入用量，会形成正反馈——超额 → 拒绝 → 拒绝本身又增加用量 → 更容易超额，配额将自我放大且永不恢复。定义 `QUOTA_CONSUMING_STATUSES = ("success", "error")` 后，被拒请求只留一条审计流水，"被拦了多少次"用按状态分组统计得出。

### 2.3 缓存命中口径（FR 命中率）

记一条 `cache_hit=1, prompt_tokens=0, completion_tokens=0` 的流水：

- 请求次数**包含**缓存命中（确实发生了一次请求）；
- Token 记 **0**（没有调用模型，没有 Token 成本）。

这样既能统计命中率，又能算出"缓存省下多少 Token 成本"。此口径已在《配额与计量说明》与实现中与成员 D 对齐（模块 D 的答复见任务书 D7）。

## 3. 流水账设计：不可变，只 INSERT（FR-D4）

**数据模型**：明细表 `usage_record` 是唯一事实来源；聚合表 `usage_summary` 的所有数值都由明细 `SUM / COUNT` **派生**，没有任何"可写计数器"。

- 计量写入路径（`app/services/metering/service.py`）只有 `db.add(record)` + `flush()`，不存在 update/delete/upsert。
- `refresh_summary()` 是**唯一**写 `usage_summary` 的入口：每次写流水后同步重算当天分桶并 UPSERT（`UNIQUE(tenant_id, bucket_date)` 保证同租户同日只有一行），成员 D 的异步任务可复用同一函数，口径不会分叉。
- **不可变性的两层保障**：模型不提供 update/delete 方法 + 表注释声明 + 静态守护测试 `test_usage_record_is_append_only` 扫描 `app/` 下所有 Python 源文件。

**为什么不用"可写计数器"`tenant.used_tokens += n`**：

1. **无法审计**：账单数字对不上时，查不出是哪一次调用写错的；
2. **并发不安全**：多个请求同时 `+=` 会丢更新，加行锁又成为性能瓶颈；
3. **无法追溯**：验收要求"账单每行数字都能在流水里查到对应记录"，计数器做不到。

不可变流水的价值：任何聚合值都能从明细重新算出，账单可逐行追溯到原始调用记录（含 `request_id`，与日志串联）。

**写入失败的处理**（与成员 B 的 HTTP 访问流水的差异）：成员 B 的 `usage_records` 是访问审计的辅助数据，写失败可以吞掉；本模块流水是**计费依据**，写失败一律显式抛出（500）+ 记 `usage_record_failed`——静默漏记会让配额永不推进，等于配额失效。

## 4. 超额行为：`reject` / `soft_warn`（FR-D6）

配置在 `tenants.overage_policy`，取值为二选一**且必须实际生效**：

| 策略 | 行为 | 响应 | 适用 |
|---|---|---|---|
| `reject` | 拒绝请求 | HTTP **429** `QUOTA_EXCEEDED`，`data` 含 `used_tokens / limit_tokens / used_requests / limit_requests / reset_at` | 硬性计费，超限即停 |
| `soft_warn` | 放行但告警 | HTTP 200 + 响应头 `X-Quota-Warning: overage`，并记 `quota_soft_overage` 日志 | 先让业务跑通，事后补费/提醒升级 |

调用点位于 `POST /api/v1/qa/ask` 的**第 1 步**（三段式顺序见 §6）。同一份超限用量，仅切换策略即得到截然不同的结果，`test_reject_policy_actually_blocks` 与 `test_soft_overage_policy_allows_request` 互为对照，证明策略不是摆设。

`429` 响应体遵循项目统一错误格式（`code / message / data`），便于前端直接展示"已用量 / 上限 / 重置时间"。

## 5. 重置机制：惰性判断 + 行锁（FR-D5）

**触发方式**：不依赖定时任务，而是在**请求路径上做幂等检查**——只要有人用，就会重置。

```python
def ensure_current_period(db, tenant):
    today = date.today()
    if (tenant.period_start.year, tenant.period_start.month) != (today.year, today.month):
        tenant.period_start = today.replace(day=1)
        db.commit()                      # 重置点：把统计窗口起点对齐到当月 1 日
```

- 统计口径 = `usage_summary.bucket_date >= tenant.period_start` 求和，因此把 `period_start` 推到当月 1 日，上个月的用量自然不再计入。
- 任何读取配额状态的入口（`/api/v1/quota/status`、`/api/v1/qa/ask`）都会先跑一次该检查。
- 验收模拟：把 `period_start` 回拨 40 天，请求后应自动回到当月 1 日（`test_period_reset_by_backdating`）。

**并发安全**：两个请求同时跨月可能重复重置，用行锁规避：

```python
tenant = db.query(Tenant).filter(Tenant.id == tenant_id).with_for_update().one()
```

> **已知边界**：`FOR UPDATE` 仅在 MySQL 生效；SQLite 按方言跳过（`db.get_bind().dialect.name != "sqlite"`），开发期无锁保护。本机 2026-10-18 已切 MySQL 并抓取确认该子句确实发出（见《运维手册》第 4 节），但**并发竞态演练仍未做**。

**为什么不用定时任务（每月 1 日 0 点）**：

| 方案 | 漏跑风险 | 实现复杂度 | 选择 |
|---|---|---|---|
| 定时任务 | ⚠️ 服务未启动/任务异常即漏跑，且**漏跑后无人发现** | 需要调度器 | ❌ |
| **惰性判断** | ✅ 只要有人用就会重置 | 简单 | ✅ |

惰性判断把"重置"从"需要外部触发的动作"变成"请求路径上的幂等检查"，可靠性显著更高。

**为什么可改 `period_start` 来模拟**：它同时是"结算窗口起点"与"是否已重置"的判据，把周期语义收敛到单个字段，因此改一个字段就能模拟跨月，无需等到下个月。

## 6. 调用链与预检位置（FR-D3）

`POST /api/v1/qa/ask` 严格三步顺序：

```text
第 1 步  配额预检        quota_service.check(db, ctx)     ← 此时绝不调用模型
            ├─ reject     → 记 quota_rejected 流水 + 抛 429（含 used / reset_at）
            └─ soft_warn  → 记 quota_soft_overage 日志 + 继续
第 2 步  查缓存          命中 → 记 cache_hit 流水（tokens=0）→ 直接返回
第 3 步  调模型          → 解析 resp.usage → 记 llm_call_completed 日志 → 记 success 流水 → 写缓存
```

**预检数据源取舍**（`check()` 读 `usage_summary` 聚合表，不 `SUM(usage_record)` 全表扫描）：

| 方案 | 准确性 | 性能 | 选择 |
|---|---|---|---|
| 每次预检 `SUM(usage_record)` | 实时准确 | ❌ 流水增长后极慢，违反 FR-F6 | ❌ |
| 读 `usage_summary` | 有刷新延迟 | ✅ 快 | ✅ 采用 |
| Redis 实时计数器 | 实时准确 | ✅ 最快 | 可作优化，但需处理与库的一致性 |

**取舍说明**：聚合表与流水同步刷新，正常路径下几乎无延迟；若成员 D 改为异步刷新，则存在刷新间隔内的延迟，意味着配额可能在临界点被"多用"一点。对企业/校园场景该误差可接受，换来的是接口响应速度。业务要求严格时可加 Redis 计数器做准实时校验，口径不变。

**鉴权与隔离（FR-C5/C6）**：`get_current_context` 支持 `X-API-Key`（优先）与 Bearer JWT 两路凭据，归一为 `RequestContext`。用 Key 调用时由 `resolve_api_key` 反查租户/用户，写入 `key_id`，并更新 `last_used_at` / `last_used_ip`（排查泄漏用，日志只记 `key_prefix`，绝不记完整 Key）。

## 7. 数据字典（DDL）

生产用 MySQL 建表语句（字段语义与实现一致）；开发期 SQLite 由 `create_all` 建表：

```sql
CREATE TABLE api_key (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  name VARCHAR(60) NOT NULL,
  key_hash CHAR(64) NOT NULL UNIQUE COMMENT 'sha256，绝不存明文',
  key_prefix VARCHAR(16) NOT NULL COMMENT '如 sk-abc123',
  key_suffix VARCHAR(8) NOT NULL COMMENT '如 xyz9',
  status VARCHAR(20) NOT NULL DEFAULT 'active' COMMENT 'active/expiring/revoked',
  expire_at DATETIME NULL COMMENT '轮换时给旧 Key 的 24h 过期时间',
  quota_monthly_tokens BIGINT NULL COMMENT 'NULL 表示继承租户配额',
  quota_monthly_requests INT NULL,
  rate_limit_per_minute INT NULL,
  rate_limit_per_hour INT NULL,
  last_used_at DATETIME NULL,
  last_used_ip VARCHAR(45) NULL,
  created_at DATETIME NOT NULL,
  INDEX idx_apikey_tenant_created (tenant_id, created_at),
  INDEX idx_apikey_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE usage_record (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  key_id BIGINT NULL COMMENT 'NULL = JWT 登录态调用',
  user_id BIGINT NULL,
  request_id VARCHAR(64) NOT NULL COMMENT '与日志 request_id 对齐，用于追溯',
  model VARCHAR(64) NOT NULL,
  prompt_tokens INT NOT NULL DEFAULT 0,
  completion_tokens INT NOT NULL DEFAULT 0,
  latency_ms INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL COMMENT 'success/error/quota_rejected',
  cache_hit TINYINT(1) NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  INDEX idx_tenant_time (tenant_id, created_at),
  INDEX idx_key (key_id),
  INDEX idx_request (request_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='不可变流水账：只允许 INSERT，禁止 UPDATE/DELETE';

CREATE TABLE usage_summary (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  bucket_date DATE NOT NULL,
  requests INT NOT NULL DEFAULT 0 COMMENT '仅 success/error（含缓存命中）',
  success INT NOT NULL DEFAULT 0,
  errors INT NOT NULL DEFAULT 0,
  prompt_tokens BIGINT NOT NULL DEFAULT 0,
  completion_tokens BIGINT NOT NULL DEFAULT 0,
  avg_latency_ms INT NOT NULL DEFAULT 0,
  p95_latency_ms INT NOT NULL DEFAULT 0,
  cache_hits INT NOT NULL DEFAULT 0,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_tenant_date (tenant_id, bucket_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`tenants` 表新增配额列：`period_start DATE NULL`、`quota_monthly_tokens BIGINT NULL`、`quota_monthly_requests INT NULL`、`overage_policy VARCHAR(20) NOT NULL DEFAULT 'reject'`。

**既有库补列**：`create_all` 不给已存在的表加列，因此 `app/db/schema.py::ensure_schema()` 在 lifespan 中用 `inspect()` 幂等补列（`ALTER TABLE tenants ADD COLUMN ...`），并记 `schema_patched` 日志。`ensure_schema()` 在 MySQL 上已随新库建表执行通过（2026-10-18），但**"缺失列 → ALTER"分支尚未触发验证**，生产迁移需单独演练。

**计量字段契约**（成员 D 的看板依赖）：`prompt_tokens` / `completion_tokens` ✅ SUM；`latency_ms` ✅ AVG / P95；`status` ✅ COUNT GROUP BY；`cache_hit` ✅ SUM；`request_id` ❌ 仅追溯。字段语义定稿后不再变更。

**账期口径同源**：`usage_record.created_at`、`usage_summary.bucket_date`、`tenant.period_start` 统一使用**服务器本地时间（naive）**，保证"自然月"边界与聚合分桶同源，避免时区错位导致月度对不上。

## 9. 评审引导（请评审人重点看这 5 点）

1. **为什么 Key 用 SHA-256 而密码用 bcrypt**
   密码是**低熵的人造字符串**（可枚举），慢哈希增加破解成本；API Key 是 **32 字节随机的高熵串**（输入空间 2^256，字典/彩虹表无意义），对高熵输入慢哈希没有额外安全收益，反而拖慢每次鉴权。鉴权路径每个请求都要校验，必须快 → SHA-256。
2. **`resolve_api_key` 的隔离例外**
   鉴权阶段还没有 `tenant_id` 上下文，却要查 `api_key` 表。方案是按**全局唯一** `key_hash` 反查（等价于按唯一键取单行），并用 bypass 极短窗口完成。**请成员 B 确认这不构成越权**——(a) 查询条件不含任何租户可控的输入；(b) 只读取一条用于定位租户的记录；(c) 拿到租户后立即写回会话上下文，后续业务查询全部走正常隔离。该例外已在代码 docstring 与本文档标注。
3. **配额预检读聚合表的取舍**
   5 分钟级（取决于刷新策略）延迟换接口响应速度，临界点可能略微多用；严格计费场景可加 Redis 计数器。详见 §6。
4. **惰性重置的并发安全**
   `ensure_current_period` 用 `with_for_update` 规避跨月重复重置；SQLite 端跳过（开发期无锁），MySQL 生效。详见 §5。
5. **流水不可变的保障**
   代码中无 update/delete 路径 + 模型不含 update 方法 + 表注释声明 + 静态守护测试。聚合值全部由明细派生。详见 §3。

## 10. 常见坑与规避（对照实现）

| 坑 | 规避 |
|---|---|
| 配额预检写在模型调用之后 | `qa.ask` 严格三步顺序，预检永远是最前面 |
| 用估算 Token（tiktoken） | 只用 `resp.usage`；缺 usage 记 0 并 `llm_usage_missing` 告警 |
| 流水表有 UPDATE 语句 | 只 INSERT；聚合由明细派生；静态测试守护 |
| Key 明文落库 | 只存 SHA-256 哈希 + 前后缀；完整值仅创建/轮换响应返回一次 |
| 列表接口也返回完整 Key | 列表只返回 `masked`（`property` 生成，非明文片段拼回） |
| 轮换时旧 Key 立即失效 | 给 24h `expire_at` 过渡窗口，新旧并行 |
| 周期重置用定时任务且漏跑 | 惰性判断，落在请求路径上 |
| 预检用 `SUM(usage_record)` | 租户口径读 `usage_summary`；Key 口径按 `key_id` 过滤流水 |
| 错误响应不含 `reset_at` | 429 `data` 必带 `used_*`、`limit_*`、`reset_at` |
| 日志打印完整 Key | 日志只记 `key_prefix`；`apikey_created` 等事件均不带完整值 |
