# 智能问答 SaaS 平台运维手册（模块 G）

> 适用版本：0.2.0；生产用 MySQL 8.0，开发可用 SQLite，由 `DATABASE_URL` 切换（本机 2026-10-18 已切 MySQL 并实测，见第 3 节）。缓存为本地内存实现。**API Key 管理与配额/计量模块（模块 C/D）已接入**：Key 可创建/轮换/吊销，配额预检在模型调用前执行。**真实模型上游已接入并跑通**（阿里云百炼的 OpenAI 兼容端点，密钥取自机器环境变量 `DASHSCOPE_API_KEY`，模型 `qwen-flash`）：`model_service` 探针为 `up`，问答返回真实答案、Token 取自模型响应的 `usage` 并落库 `usage_record`。旧模型 `qwen-turbo` 会被限流（429 `limit_requests`，属速率限流而非余额不足），后端如实映射为 502 `MODEL_SERVICE_ERROR`。未配置 `MODEL_BASE_URL` 时仍回退内置本地模拟模型（`provider=local-simulation`），用量如实标注来源，不把桩服务视作真实依赖正常。

## 1. 启动、健康检查与日志

从 `问答平台/backend` 目录执行：

```bash
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
curl -s http://127.0.0.1:8000/health
```

健康检查返回 `dependencies.database / model_service / cache` 三项；全部 `up` 时 HTTP 200 和 `status=ok`，任一异常/未配置则 HTTP 503 和 `status=degraded`。本地未配置 `MODEL_BASE_URL` 时模型探针为 `unconfigured`，这是真实状态，不应当谎报为 `up`。探测超时由 `HEALTH_TIMEOUT_SECONDS` 控制（默认 3 秒）；数据库、缓存探测使用线程避免阻塞事件循环。配置真实模型后探测 `GET ${MODEL_BASE_URL}/models`（OpenAI 兼容面里普遍可用，百炼等真实供应商没有 `/health`），只接受 2xx 为正常。

结构化日志：`LOG_JSON=true` 默认输出单行 JSON，含 `ts / level / event / request_id / tenant_id / key_prefix / path / method / status_code / elapsed_ms`。可由响应头 `X-Request-Id` 串联日志。日志不得输出 Authorization 头、完整 API Key、密码、请求体。`LOG_LEVEL` 可设置 INFO/WARNING/ERROR；开发调试 SQL 使用 `DB_ECHO=true`，生产勿开启（SQL 参数可能含敏感数据）。

### 2026-10-18 真实模型上游接入实测

接入阿里云百炼（DashScope）OpenAI 兼容端点后实测：

- 配置：`MODEL_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1`，`MODEL_NAME=qwen-flash`，`MODEL_API_KEY` 留空并由 `app/config.py` 回退到环境变量 `DASHSCOPE_API_KEY`（密钥不入库、不入 `.env`）。
- 探针：健康检查的 `/health` 改为请求 `GET /models`（与 `/chat/completions` 同一 OpenAI 兼容面；百炼没有 `/health`），返回 `model_service: up`，整体 HTTP 200。
- 问答：`POST /api/v1/qa/ask` 返回 `model_provider=openai-compatible`、`tokens={prompt_tokens:198, completion_tokens:15, total_tokens:213}`、`latency_ms=685`、`sources` 3 条，答案为基于知识片段的中文回答。
- 计量：`usage_record` 落库 `model=qwen-flash` 且 Token 与响应 `usage` 一致（**非估算**）；失败的调用如实记为 `status=error` 且 Token 为 0。
- **踩坑记录**：`qwen-turbo` 返回 429 `limit_requests`（"You have exceeded your current request limit"）。按官方《限流》文档，429 是 **RPM/TPM 速率限流**，与余额无关——欠费是 400 `Arrearage`，免费额度耗尽（开启"用完即停"后）是 403。换成 `qwen-flash` / `qwen-plus` / `qwen3.6-flash` 后同账号立即调用成功。
- 测试：`python -m pytest tests -q` → **71 passed**；`test_health_unconfigured_model_returns_degraded` 原先依赖"未配置上游"的环境假设（并会真实发起网络请求），已改为 `monkeypatch` 显式清空 `MODEL_BASE_URL`，测试不再依赖开发机的 `.env`。

## 2. 五类错误码

| 类型 | 代码 | HTTP | 处理方式 |
|---|---|---:|---|
| 配额 | `QUOTA_EXCEEDED` | 429 | 核对当前周期及明细，升级套餐或等待周期刷新 |
| 限流 | `RATE_LIMITED` | 429 | 客户端指数退避，检查突发流量 |
| 鉴权 | `UNAUTHORIZED`、`INVALID_TOKEN`、`FORBIDDEN` | 401/403 | 检查登录态、角色；跨租户资源仍返回 404 |
| Key 失效 | `API_KEY_INVALID`、`API_KEY_REVOKED` | 401 | 轮换/吊销后改用新 Key |
| 模型异常 | `MODEL_SERVICE_ERROR` | 502 | 检查上游健康探针、超时和供应商状态 |

目前上述错误码定义及统一异常格式已实现。**API Key 生命周期（创建/轮换/吊销）与配额预检已接入并即时生效**：吊销或过期 Key 调用返回 401 `API_KEY_INVALID`，超配额返回 429 `QUOTA_EXCEEDED`（`data` 含已用量与 `reset_at`）。**限流与真实模型问答均已接入**：滑动窗口限流（Key 与租户双维度）在模型调用前执行，超限返回 429 `RATE_LIMITED` 并附 `retry_after`（秒），见第 1 节；真实模型上游（阿里云百炼 OpenAI 兼容端点）已跑通，实测记录见第 1 节「真实模型上游接入实测」。限流为进程内实现，多 worker 部署须切 Redis 共享计数。

## 3. 备份与恢复


### MySQL（生产环境切换后）

```bash
export BACKUP_MODE=mysql DB_HOST=127.0.0.1 DB_PORT=3306 DB_USER=backup DB_NAME=smartqa_saas
export DB_PASSWORD='从安全凭据管理系统获取，不要写入脚本/文档'
bash scripts/backup/backup.sh
# 先停服/确认恢复范围，严禁在未备份或未授权时执行：
ALLOW_RESTORE_PRODUCTION=YES bash scripts/backup/restore.sh backups/smartqa_saas_YYYYmmdd_HHMMSS.sql.gz
```

MySQL 使用单事务导出并 gzip 完整性检查，恢复需显式授权；密码走 `MYSQL_PWD` 环境变量而非 `-p密码` 进程参数（环境变量仍可能被高权限进程读取，应改为短期凭证/专用账号）。**MySQL 备份恢复尚未实际验证**，上线前必须在独立测试库演练。

## 4. 故障场景与处置

| 场景 | 现象与排查 | 处置 |
|---|---|---|
| 数据库连接失败 | `/health` 的 `database=down`；核对 `DATABASE_URL`，用数据库客户端连接，查服务/防火墙/磁盘空间 | 修复连接或启动服务；损坏时仅在备份和审批后恢复副本 |
| 模型服务超时 | `model_service=down` 且 `reason=timeout`；探测上游 `/health`、网络/DNS、凭据是否过期 | 切备用服务或短暂降级；检查 `MODEL_TIMEOUT_SECONDS` 与供应商契约 |
| 用量/配额异常 | `/api/v1/quota/status` 与 `/api/v1/usage/by-key` 与预检结果不符；排查同租户、周期、Key 口径与错误率 | 核对 `usage_record` 明细与 `usage_summary` 聚合（聚合必须由明细派生），确认 `tenant.period_start` 是否为当月 1 日；修复后重算聚合 |
| API Key 泄漏 | 用量异常攀升；查 `api_key.last_used_at`/`last_used_ip`、请求时间分布、Key 前缀，不查/不传播完整 Key | 立即吊销泄漏 Key 并轮换，检查异常流量，通知租户；具体步骤见第 5 节 |
| 缓存跨租户串数据 | 不同租户看见同一答案；检查 `tenant_key(tenant_id, ...)`、缓存命中日志 | 停用相关缓存，按 `t:<tenant_id>:` 前缀清理，修复构键方式，补跨租户测试 |
| 隔离失效 | 租户读到他人资源；检查业务表继承 `TenantMixin`、ORM SQL、静态绕过检查 | 暂停相关接口，修复数据层与测试，排查原生 SQL / engine 直连；再次运行测试报告 |
| 用量写入失败 | `usage_record_failed` 日志、用量漏记；检查数据库容量/迁移状态 | 成员 B 的 HTTP 访问流水写失败可吞掉（请求仍返回成功）；**模块 C/D 的计量流水是计费依据，写失败会显式返回 500 并记 `usage_record_failed`**，须修复数据库后回补流水并重算 `usage_summary` |

## 5. Key 泄漏应急命令级流程（模块 C 已接入）

撤销接口为 `DELETE /api/v1/apikeys/{key_id}`，**吊销立即生效**（同一进程内下一次请求即 401，无需等缓存过期）。禁止以删除用户/租户来代替精确吊销。

```bash
BASE_URL=http://127.0.0.1:8000
ADMIN_TOKEN='<租户管理员 JWT，从受控渠道获取>'

# 1. 先定位 Key 记录：只查前缀/后缀/最后使用时间与来源 IP，禁止把完整 Key 粘贴到终端或工单
#    列表接口只返回掩码，可用于核对；确认泄漏的是哪一条 key_id
curl -s "$BASE_URL/api/v1/apikeys" -H "Authorization: Bearer $ADMIN_TOKEN"

# 2. 吊销泄漏 Key（key_id 用上一步确认的值）
curl -s -X DELETE "$BASE_URL/api/v1/apikeys/<泄漏的 key_id>" \
  -H "Authorization: Bearer $ADMIN_TOKEN"

# 3. 用受控测试请求验证旧 Key 已失效：应返回 401 且 code=API_KEY_INVALID
curl -s -X POST "$BASE_URL/api/v1/qa/ask" \
  -H "X-API-Key: <被吊销的 Key>" -H "Content-Type: application/json" \
  -d '{"question":"revocation check"}'

# 4. 生成替代 Key（响应中的完整值仅此一次可见，立即写入调用方保密配置，勿落日志）
curl -s -X POST "$BASE_URL/api/v1/apikeys" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"替代 Key（事故 2026-10-15）","quota_monthly_tokens":100000}'
# 验证新 Key 可用：POST /api/v1/qa/ask 带 X-API-Key，应返回 200

# 5. 从日志按 request_id / key_prefix 定位异常时间窗，冻结相关异常流量并通知租户
```

补充说明：

- 需要**灰度切换**而非停机的场景，用轮换 `POST /api/v1/apikeys/{key_id}/rotate`：旧 Key 获得 24h `expire_at` 过渡窗口，新 Key 立即可用并继承旧 Key 的配额与限流配置；窗口结束后旧 Key 自动失效。
- 泄漏 Key 的历史用量可在 `GET /api/v1/usage/by-key` 按 `key_id` 分组查看。
- 禁止在日志、终端或工单中出现完整 Key；人工排查只允许使用前缀（`sk-` + 8 位）与最后 4 位。

> **仍需注意**：限流（滑动窗口，Key 与租户双维度）已接入并即时生效，泄漏期间可先借限流压低异常流量，再走吊销 + 轮换的应急流程完成止血。限流为进程内实现，多 worker 部署须切 Redis 共享计数，否则各 worker 独立计数会稀释限流效果。

## 6. 隔离自测与已知绕过点

```bash
# 在 backend 目录（全量：隔离 + 可观测性 + API Key/配额计量）
python -m pytest tests -q
```

`TenantMixin` 只保护 SQLAlchemy ORM 访问；原生 `text(...)`、engine 直连会绕过；健康检查的 `SELECT 1` 是**仅有的已登记 Core SQL 豁免**，其不读租户业务表。`seed` 以独立 Session 显式设置 `tenant_bypass` 做维护；无租户上下文的业务表 ORM 查询/写入 fail-closed，身份层（User/Role/Tenant）不混入 `TenantMixin`。超管绕过仅在 `require_super_admin` 确认实时角色后生效，请求结束自动复位。别名查询 `include_aliases=True`，关联、聚合、写入与用量记录均在测试中覆盖。

**模块 C/D 的已登记隔离例外**：`resolve_api_key` 在鉴权阶段（尚无租户上下文）按**全局唯一**的 `key_hash` 反查 `api_key` 一行，并以 bypass 极短窗口完成——查询条件不含任何租户可控输入，只取一条用于定位租户的记录，随后立即写回会话上下文，后续业务查询全部走正常隔离。该例外待成员 B 评审确认，详见《配额与计量说明》第 9 节。

当前测试结果：全量 **71 passed / 0 failed**（隔离 19 + 可观测性 12 = 31 条、API Key 与配额计量 20 条、看板与账单 6 条、限流与缓存 6 条、平台配额管理与角色身份 8 条），详见 `backend/tests/reports/isolation_report.md` 与 `backend/tests/reports/quota_report.md`（后两份为当时批次的运行记录，条目数不含后续新增模块）。
