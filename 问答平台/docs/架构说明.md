# 架构说明

> 智能问答 SaaS 平台 · 分层架构与数据流（模块 A 交付物，D9 定稿）

---

## 1. 分层总览

请求自上而下穿过四层，每一层都有明确职责与"不可绕过的入口函数"：

| 层 | 职责 | 关键文件 | 入口 |
|---|---|---|---|
| **鉴权层** | 解析凭据 → 产出 `RequestContext`（含 `tenant_id` / `role`） | `app/deps.py`、`app/security.py`、`app/core/context.py` | `get_current_context()`、`require_admin()`、`require_super_admin()` |
| **隔离层** | 把 `tenant_id` 注入 ORM，读写双向 fail-closed | `app/db/tenant_hook.py`、`app/db/base.py` | ORM 事件 `do_orm_execute` / `before_flush` |
| **限流层** | 按租户 + Key 双维度滑动窗口计数 | `app/services/rate_limit.py`、`app/services/cache/backend.py` | `enforce()` |
| **计量层** | 配额预检、不可变流水、聚合汇总、看板与账单 | `app/services/quota/`、`app/services/metering/`、`app/tasks/summary.py`、`app/services/billing/` | `quota_service.check()`、`metering.record_*`、`refresh_summary()` |

```
                    ┌──────────────────────── 请求 ────────────────────────┐
HTTP ─▶ RequestContextMiddleware(注入 X-Request-Id、写访问流水)
                    │
                    ▼
              ┌───────────┐   get_current_context()
              │  鉴权层   │   X-API-Key 优先,否则 JWT;登出黑名单校验
              └───────────┘   └─▶ db.info["tenant_id"] = ctx.tenant_id  ★隔离层的唯一输入
                    │
                    ▼
              ┌───────────┐   配额预检(先) → 查缓存 → 调模型
              │  限流层   │   Key 维度 / 租户维度;超限 429 + Retry-After
              └───────────┘
                    │
                    ▼
              ┌───────────┐   record_success / record_error / record_cache_hit
              │  计量层   │   流水只 INSERT;后台线程汇总进 usage_summary
              └───────────┘
                    │
                    ▼
              ┌───────────┐   with_loader_criteria 注入 tenant_id 条件
              │  隔离层   │   before_flush 拒绝跨租户写入
              └───────────┘
                    │
                    ▼
               业务表(KnowledgeBase / Document / ApiKey / usage_record / usage_summary)
```

## 2. 鉴权层

### 2.1 数据契约

```python
@dataclass
class RequestContext:
    request_id: str
    user_id: int | None
    tenant_id: int | None   # 隔离层唯一数据来源
    role: str               # super_admin / admin / readonly
    key_id: int | None = None
    key_prefix: str | None = None
```

JWT payload 固定字段：`sub`（user_id 字符串）、`tenant_id`（整数）、`role`、`jti`（登出黑名单）、`iat`、`exp`。
**这三个字段语义不可变更**，需要扩展只能追加字段。

### 2.2 关键决策

| 决策 | 原因 |
|---|---|
| 密码用 bcrypt 而非 SHA-256 | 慢哈希 + 自动加盐，显著抬高撞库成本；验收要求库中值为 `$2b$` 开头 |
| 主动登出用 jti 黑名单 | JWT 无状态，撤销必须引入服务端状态；黑名单只存已登出项，惰性清理 |
| 上下文挂 `session.info` 而非 `ContextVar` | 同步端点跑在线程池，依赖与端点可能不同线程，`ContextVar` 传递不可靠；同一请求内 FastAPI 依赖缓存复用同一 Session，`session.info` 随 Session 走最稳 |
| 租户条件不手写进 SQL | 写死在端点里迟早漏一处；统一由 ORM 事件注入，端点代码"看不见"租户条件 |

> **已知限制**：黑名单为进程内字典，多 worker 部署不共享；生产须切 Redis。

## 3. 隔离层（模块 B）

### 3.1 写入路径（fail-closed）

`before_flush` 对 `session.new ∪ dirty ∪ deleted` 中的 `TenantMixin` 对象逐一检查：

1. 无租户上下文 → 拒绝（`TENANT_CONTEXT_REQUIRED`，500）；
2. 对象未填 `tenant_id` → 自动补全为上下文租户；
3. 对象 `tenant_id` ≠ 上下文租户 → 拒绝（`TENANT_ISOLATION_VIOLATION`，403）。

批量 ORM DML（`update`/`delete`/`insert` 语句）会绕过对象级守卫，因此**直接禁止**，
强制"先查询（已被过滤）再修改对象"。

### 3.2 读取路径

`do_orm_execute` 对 `TenantMixin` 子类的 SELECT 用 `with_loader_criteria(cls.tenant_id == tid)`
把租户条件追加进 WHERE：主查询、子查询、join 全部生效，且随对象传播到关系加载。

无上下文的业务表查询同样 fail-closed（防止未鉴权的裸查询绕过隔离）。

### 3.3 显式绕过

`bypass_tenant_filter(session)` **只允许在 `require_super_admin` 授权后使用**（平台租户列表、seed 脚本）。
它是显式、可审计的窄口，不是"默认放行开关"。

### 3.4 越权语义

跨租户访问他人资源统一返回 **404**（与"资源不存在"同码），避免通过状态码泄露资源存在性；
而角色不足返回 **403**。两者语义不同，不可混用。

## 4. 限流层（模块 E）

### 4.1 双维度

| 维度 | 阈值来源 | 适用 |
|---|---|---|
| API Key | `ApiKey.rate_limit_per_minute` / `per_hour` | 带 `X-API-Key` 的调用 |
| 租户兜底 | `settings.TENANT_RATE_LIMIT_PER_MINUTE` / `PER_HOUR`（默认 600 / 20000） | JWT 登录态调用 |

`enforce(tenant_id, key_id, per_minute, per_hour)` 返回 `(allowed, retry_after, window)`。
被拒时抛 `BizError("RATE_LIMITED", ..., 429, {"retry_after": n})`，
由 `main.py` 的异常处理器补回标准 **`Retry-After`** 响应头（`raise` 会丢弃端点上的 `Response` 对象）。

> 计数窗口为进程内 `defaultdict(deque)` + 锁；多 worker 部署各自独立计数，生产须切 Redis。

### 4.2 缓存

`InMemoryCache` + `tenant_key(tenant_id, ...)` 生成 `t:{tenant_id}:qa:{question}`，
**租户前缀置于最前**，物理上不可能跨租户命中。
问答缓存命中时 `X-Cache: HIT`、Token 计 0、仍返回引用来源。

## 5. 计量层（模块 C/D/F）

### 5.1 问答三步顺序（不可调换）

1. **限流** → 2. **配额预检**（此时绝不调用模型）→ 3. **查缓存** → 4. **调模型**。

任何"先调模型再判配额"的写法都会白烧上游 Token，并被 `test_quota.py::test_quota_rejected_without_model_call`
的计数器断言判为不合格。

### 5.2 两张易混表

| 表名 | ORM 类 | 用途 | 写入时机 |
|---|---|---|---|
| `usage_record` | `LlmUsageRecord` | **计费流水**：模型、Token、延迟、状态、缓存命中 | 每次问答（成功/失败/缓存命中/配额拒绝） |
| `usage_records` | `UsageRecord` | **HTTP 访问流水**：方法、路径、状态码、耗时 | 中间件按请求 |

`usage_record` **只 INSERT，永不 UPDATE/DELETE**（FR-D4）。既有测试用静态扫描断言 `app/` 下不存在对其的 UPDATE/DELETE。

### 5.3 Token 口径

**只用模型响应返回的 `usage`，绝不估算**。模型未返回 usage 时记 0 并打 `llm_usage_missing` 告警，
日志字段 `usage_source` 标明来源（`response.usage`），供验收 `grep` 佐证（FR-D2）。

### 5.4 配额与周期

- 维度：月度 Token、月度请求数，任一超限即按策略处理；
- 策略：`reject`（429 拦截）/ `soft_warn`（放行 + `X-Quota-Warning: overage`）；
- 重置：**惰性判断**——读取配额时若 `period_start` 落于上个月，则重置回当月 1 日并清零计数，无需定时任务；
- 被拒请求记一条 `quota_rejected` 流水（0 Token / 0 耗时），该状态**不计入配额消耗**，避免拒绝自我放大。

### 5.5 汇总与看板（模块 F）

```
usage_record(明细) ──refresh_summary()──▶ usage_summary(按 租户+自然日 聚合)
                                              │
                            看板标量指标/趋势 ─┘（只读汇总表，耗时恒定）
```

- `app/tasks/summary.py` 用标准库 `Thread` + `Event` 起后台线程，按 `SUMMARY_REFRESH_INTERVAL_SECONDS`
  （默认 300s）回看 `SUMMARY_REFRESH_LOOKBACK_DAYS`（默认 2 天）窗口调用 `refresh_all()`；
  **不新增 apscheduler 依赖**。`interval <= 0` 时不启动（仅手动刷新）。
- 每个租户一个 Session 并显式设置 `db.info["tenant_id"]`（**不用 bypass**），后台任务同样受隔离约束。
- 多进程部署时定时器会在每个进程各起一个，建议改为独立 worker 进程执行（见 `app/tasks/summary.py` docstring）。

**标的与取舍**：看板的标量指标与趋势只读 `usage_summary`；
`by_key`（汇总表无 Key 维度）与 `latency_distribution`（汇总表无分布字段）无法从汇总表得出，
只能在**有界时间区间**内聚合明细表——所有对 `usage_record` 的查询都强制带 `created_at >=` / `<` 条件，
由 `tests/test_dashboard_billing.py` 抓取实际 SQL 断言固化该约束（FR-F6）。

**代价**：看板数据有最多 5 分钟延迟，换取接口耗时恒定。

### 5.6 账单与可追溯（FR-F5）

- `parse_period()` 支持 `today/week/month/YYYY-MM/YYYY-MM-DD`，解析为左闭右开 `[start, end)`；
- `build_bill()` 从 `usage_summary` 派生合计（平均延迟按请求数加权，P95 取各日最大值）；
- `verify_bill_traceable()` 把"人工抽查"变成**自动化断言**：逐个字段比对 `build_bill` 结果
  与 `usage_record` 侧的 `COUNT/SUM`（仅计入消耗配额的状态），返回 `traceable` 与 `mismatches`；
- 导出 CSV/Excel（`openpyxl`，缺失时降级 CSV），每行带 `request_id` 可逐行回查。

## 6. 可观测性

- 日志默认 JSON，字段含 `X-Request-Id`、租户、路径、状态码、耗时；**绝不记录完整 Key 或密码**（只记 `key_prefix`）；
- 模型调用日志带 `usage_source`、`model_provider`，用于证明 Token 非估算；
- `GET /health` 单次探测超时（`HEALTH_TIMEOUT_SECONDS`），依赖不可用时返回 503 而非"假装健康"。

登录态存 `localStorage` 的 `smartqa_token` / `smartqa_role` / `smartqa_tenant`。

> 路由守卫与请求封装已统一从 `src/api/index.js` 导出常量，避免散落的字面量。

## 8. 数据流：一次问答请求

```
1. 中间件     生成 request_id,写 HTTP 访问流水(usage_records)
2. 鉴权层     get_current_context() → X-API-Key 或 JWT → RequestContext
3. 隔离输入   db.info["tenant_id"] = ctx.tenant_id
4. 限流层     enforce(tenant_id, key_id, ...) → 超限 429 + Retry-After(异常处理器补头)
5. 计量层     quota_service.check() → 惰性周期重置 → 超限:记 quota_rejected 流水 + 抛 QUOTA_EXCEEDED
6. 缓存       tenant_key(tid, "qa", question) → 命中:记 cache_hit 流水(0 Token) + X-Cache: HIT
7. 模型       rag.retrieve_context(隔离层自动注入本租户语料) → llm_client.complete()
8. 计量层     metering.record_success(...) 取响应 usage 记流水
9. 隔离层     before_flush 校验 tenant_id 一致 → 落库
10. 后台线程  按周期把 usage_record 汇总进 usage_summary → 供看板/账单读取
```
