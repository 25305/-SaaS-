# 隔离验证报告(模块 B:多租户数据隔离)

- 项目:智能问答 SaaS 平台
- 生成日期:2026-10-12
- 对应需求:FR-B1 ~ FR-B5(需求文档 3.2 节)
- 实现位置:`backend/app/tenant_scope.py`(隔离机制)、`backend/app/models.py`(TenantMixin)

## 1. 方案选择与取舍(FR-B1)

| 维度 | 行级隔离(本项目采用) | 库级隔离(每租户独立 schema/库) |
|---|---|---|
| 实现方式 | 所有业务表带 `tenant_id` 列,查询统一注入租户条件 | 每租户建独立数据库,连接串按租户切换 |
| 隔离强度 | 强,但依赖"每次查询都带条件"(由 ORM 事件强制保证) | 最强,物理隔离 |
| 成本与复杂度 | 低:一套表结构、一个连接池 | 高:建库/迁移/备份/连接管理都按租户复制 |
| 租户动态注册 | 天然支持,新租户只是新数据行 | 每次注册要建 schema、维护映射 |
| 平台全局统计 | 简单:去掉过滤条件即可聚合全量 | 需要跨库聚合,复杂 |
| 开发期环境 | SQLite 单文件即可跑通 | SQLite 无法演示,需先上 MySQL 并管理多库 |

**结论**:本项目为课程规模的 SaaS 平台,租户是动态注册的,且后续模块需要平台级全局统计(模块 F),选择**行级隔离 + 数据访问层统一注入**。库级隔离的物理彻底性在本场景下收益有限、成本过高。

## 2. 隔离机制实现(FR-B2)

隔离不依赖每个接口手写 `where tenant_id=...`,而是在数据访问层用 **SQLAlchemy ORM 事件钩子**统一实现,共两道防线:

### 2.1 查询防线:`do_orm_execute` 事件自动注入租户条件

```python
@event.listens_for(Session, "do_orm_execute")
def _inject_tenant_criteria(execute_state):
    tid = execute_state.session.info.get(TENANT_ID_KEY)
    if tid is None or execute_state.session.info.get(TENANT_BYPASS_KEY):
        return
    if execute_state.is_select:
        if execute_state.is_column_load or execute_state.is_relationship_load:
            return
        if not execute_state.is_orm_statement:
            return
        execute_state.statement = execute_state.statement.options(
            with_loader_criteria(
                TenantMixin,
                lambda cls: cls.tenant_id == tid,
                include_aliases=True,
            )
        )
```

- 所有继承 `TenantMixin` 的表(知识库、文档、以及模块 D 的用量流水),其 SELECT 都会被自动追加 `tenant_id = 当前租户` 条件,对主查询、子查询、join、聚合查询全部生效;
- `with_loader_criteria` 接受未映射的 mixin 基类,会自动展开到每一个映射子类(已对照 SQLAlchemy 2.0.36 源码核实);
- 端点代码里**不需要也不允许**手写租户条件,`routers/kb.py` 中的取数写法是 `select(KnowledgeBase).where(KnowledgeBase.id == kb_id)` —— 只有业务条件,租户条件由钩子注入,代码走查可证(FR-B2 验收)。

### 2.2 写入防线:`before_flush` 事件把守对象级写入

```python
@event.listens_for(Session, "before_flush")
def _guard_tenant_writes(session, flush_context, instances):
    tid = session.info.get(TENANT_ID_KEY)
    if tid is None or session.info.get(TENANT_BYPASS_KEY):
        return
    for obj in session.new.union(session.dirty).union(session.deleted):
        if not isinstance(obj, TenantMixin):
            continue
        if obj.tenant_id is None:
            obj.tenant_id = tid          # 漏填自动补全到当前租户
        elif obj.tenant_id != tid:
            raise BizError("TENANT_ISOLATION_VIOLATION", "检测到跨租户数据写入", 403)
```

- 端点漏填 `tenant_id` → 自动补全为当前租户,不会写错租户;
- 端点显式填了**别的租户**的 `tenant_id` → 立即拒绝(403),fail-closed。

### 2.3 批量 ORM DML 禁止

`db.execute(update/delete/insert(...))` 这类批量语句不经对象守卫,可能绕过隔离,因此在 `do_orm_execute` 中检测到租户上下文下的 ORM DML 一律抛错(500),强制"先查询(已被过滤)再修改对象"的写法。全项目现有代码无此用法,零破坏。

### 2.4 租户上下文为什么放在 `session.info` 而不是 ContextVar

FastAPI 的同步 `def` 端点运行在线程池,依赖函数与端点函数**可能不在同一线程**,ContextVar 无法可靠传递;而同一请求内 FastAPI 的依赖缓存会复用同一个 SQLAlchemy Session 对象,`session.info` 挂在 Session 上随请求走,最可靠。上下文由 `deps.get_current_user` 在加载用户前写入:

```python
db.info[TENANT_ID_KEY] = int(tenant_id)   # 取自 JWT payload
```

## 3. Fail-closed 规则清单

| 场景 | 行为 |
|---|---|
| token 缺少 tenant_id | 401 INVALID_TOKEN(不设上下文,杜绝"静默不过滤") |
| token 租户与用户实际租户不一致 | 401 INVALID_TOKEN(token 与租户绑定) |
| 写入对象 tenant_id 与上下文不一致 | 403 TENANT_ISOLATION_VIOLATION |
| 租户上下文下使用批量 ORM DML | 500 TENANT_ISOLATION_VIOLATION |
| 无租户上下文(登录/注册/种子) | 放行(身份层流程需要全局查询) |
| 跨租户按 ID 查询 | 与"资源不存在"完全相同的 404(FR-B3) |

## 4. 平台管理员的绕过机制

平台管理员(super_admin)需要全局视角(租户列表、模块 F 的全局统计),其请求由 `require_super_admin` 依赖在**同一个 Session** 上设置绕过标记:

```python
db.info[TENANT_BYPASS_KEY] = True
```

- 绕过标记是请求级的,只存在于内存中的 Session,不落库;
- 只有经过 `require_super_admin` 校验(实时读库确认角色)的请求才会设置,普通管理员/只读成员拿不到;
- 超管自己的 token 访问普通接口时仍按 platform 租户过滤,不会意外看到别的租户数据。

## 5. 为什么 User/Role/Tenant 不继承 TenantMixin

`User/Role/Tenant` 属于**身份与权限层**,不是业务数据层,必须支持全局查询:

- 登录要按用户名**全局**查用户;
- 注册/创建成员要做**全局**用户名查重——若 User 也被注入租户条件,查重会退化成"仅本租户查重",跨租户重名将绕过检查、在 INSERT 时撞 `username unique` 约束变成 500(正确行为是 409);
- 种子数据在无租户上下文的 Session 中写入。

业务数据层(知识库、文档、模块 D 用量流水)全部继承 `TenantMixin`,新模块"继承即隔离"(FR-B4 的结构性保证)。

## 7. 已知边界与约定

- **identity-map 命中路径**:同一 Session 内已加载的对象再次 `Session.get()` 不发 SQL、不再过滤,但每请求新建 Session,对象必是本请求内已被过滤加载的,安全。
- **commit 后回读**:`expire_on_commit` 的列刷新按主键回读"已通过过滤"的对象,安全;端点取新建对象 id 采用 `db.flush(); new_id = ...; db.commit()` 模式。
- **纯 Core SQL 不适用**:约定项目内一律使用 ORM 查询;钩子对不含 ORM 实体的纯 Core 语句不处理。
- **模块 D 接入方式**:用量流水表继承 `TenantMixin` 即自动获得读写隔离;平台级全局统计走 `require_super_admin` 的绕过标记。
- **种子脚本独立运行**:`scripts/seed.py` 不经过 `app.main` 时事件未注册,但其 Session 本无租户上下文,行为一致。
- 前端路由守卫(FR-A6)属模块 H;全局用量看板属模块 F。

## 9. 结论

- 行级隔离策略选型合理,取舍已文档化;
- 隔离在数据访问层统一实现:查询靠 `do_orm_execute` 注入、写入靠 `before_flush` 守卫、批量 DML 禁止,端点零手写租户条件;
- 越权测试脚本 27 项跨租户攻击全部被拒绝、0 信息泄露,隔离有效。
