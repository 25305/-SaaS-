# 数据库设计：多租户隔离策略

## 隔离策略选型

| 维度 | 行级隔离（共享 schema） | 库级隔离（每租户独立库） |
|---|---|---|
| 隔离强度 | 依赖 ORM 钩子及严格代码审查；原生 SQL 可绕过 | 数据库连接本身形成隔离 |
| 新增租户 | 新增租户记录即可 | 创建库并同步 schema/迁移 |
| 迁移成本 | 每张表升级一次 | 每个租户各升级一次 |
| 跨租户统计 | 通过授权的超管会话统一聚合 | 需跨库读取与汇总 |
| 运维成本 | 一个连接池和备份流程 | 随租户数增加的连接与备份流程 |

**结论：选择行级隔离。** 当前是课程规模的 3 个演示租户，库级隔离的物理优势不足以抵消迁移与运维开销。行级隔离的风险是漏加 `tenant_id`：本项目用 `app/db/tenant_hook.py` 中的 `do_orm_execute` 对 `TenantMixin` 的 ORM SELECT 统一注入 `tenant_id`，`before_flush` 守卫写入并禁止批量 ORM DML，缺少租户上下文时业务表访问失败关闭（fail-closed）。这大幅减少漏隔离风险，但**不能宣称彻底消除**：原生 SQL、engine 直连、未来不混 mixin 的模型仍是评审重点。

## 模型与索引契约

- 身份层 `Tenant / User / Role` 是受控白名单，不继承 `TenantMixin`；登录、用户名全局去重、租户管理需访问身份层。`Tenant` 上挂配额配置列（`period_start` / `quota_monthly_tokens` / `quota_monthly_requests` / `overage_policy`），作为租户级配额与周期起点。
- 业务层 `KnowledgeBase / Document / UsageRecord / ApiKey / LlmUsageRecord / UsageSummary` **全部继承 `TenantMixin`**，每个实例必须有 `tenant_id`。
- 每个业务表显式声明 `(tenant_id, created_at)` 复合索引，供租户等值匹配 + 时间范围扫描（`ix_kb_tenant_created`、`ix_doc_tenant_created`、`ix_usage_tenant_created`、`ix_apikey_tenant_created`、`ix_llmusage_tenant_created`）。ORM 模型定义同时作为 SQLite 开发期建表来源；MySQL 生产迁移需单独验证。
- `UsageRecord`（表 `usage_records`）是成员 B 的 HTTP 访问流水，存租户 ID、方法、路径、状态码、请求耗时与创建时间；`api_key_id` 已由模块 C 写入（用 Key 调用时记该 Key，JWT 调用为 NULL）。`/api/usage/summary` 与 `/api/usage/records` 都是 ORM 查询，自动隔离。
- 模块 C/D 新增三张表（字段与索引详见《配额与计量说明》第 7 节）：
  - `api_key`：Key 元数据，只存 SHA-256 `key_hash`（唯一）+ `key_prefix` + `key_suffix`，**绝不存明文**；含 Key 级配额/限流列、`expire_at`（轮换过渡窗口）、`last_used_at` / `last_used_ip`（泄漏排查）。
  - `usage_record`（模型为 `LlmUsageRecord`，区别于上表 `usage_records`）：**不可变计量流水，只允许 INSERT**，记录 `key_id` / `request_id` / `model` / `prompt_tokens` / `completion_tokens` / `latency_ms` / `status` / `cache_hit`；`prompt_tokens`+`completion_tokens` 均取自模型响应 `usage`，不估算。
  - `usage_summary`：由明细 `SUM / COUNT` 派生的日聚合，`UNIQUE(tenant_id, bucket_date)` 保证同租户同日一行；没有任何可写计数器。`usage_summary` 由成员 D 的异步看板或本模块 `refresh_summary` 写入，**表结构由 C 定稿**。

> 命名易混点：`usage_records`（模块 B，HTTP 访问审计，写失败可吞）与 `usage_record`（模块 C/D，计费依据，写失败显式 500）是两张不同的表，不要混用。

## 审计与已知绕过点

- `get_current_user` 从经签名验证的 JWT 读出租户，核对数据库中的用户所属租户，再将租户 ID 传给请求 Session；`Session.get` 的 identity map 命中仅适用于请求内已读出的对象。
- `require_super_admin` 实时核验平台角色后，在当前 Session 打开跨租户绕过；独立的 `seed` Session 显式声明维护级绕过。业务接口不得调用绕过 API。
- `app/api/v1/health.py` 的 `SELECT 1` 是**已登记的 Core SQL 豁免**，不读业务表。任何其他 raw SQL 或 engine 直连绕过必须走专项评审和租户条件审查；当前静态守护测试扫描业务路由。
- **模块 C 的已登记隔离例外**：`app/services/apikey/service.py::resolve_api_key` 在鉴权阶段（尚无 `tenant_id` 上下文）按**全局唯一** `key_hash` 反查 `api_key` 一行，用 bypass 极短窗口完成——查询条件不含租户可控输入，只取一条用于定位租户，随后立即把租户写回会话上下文。该例外待成员 B 评审确认，详见《配额与计量说明》第 9 节。
- 复合索引在既有库上由 `create_all` 补建；`tenants` 的配额列由 `app/db/schema.py::ensure_schema()` 用 `ALTER TABLE` 幂等补齐（既有库升级路径）。需启动应用或显式执行迁移后才能确认列/索引已存在。不要在未备份生产库时直接运行迁移。
