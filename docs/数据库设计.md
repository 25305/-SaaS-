# 数据库设计：多租户隔离策略

## 隔离策略选型

| 维度 | 行级隔离（共享 schema） | 库级隔离（每租户独立库） |
|---|---|---|
| 隔离强度 | 依赖 ORM 钩子及严格代码审查；原生 SQL 可绕过 | 数据库连接本身形成隔离 |
| 新增租户 | 新增租户记录即可 | 创建库并同步 schema/迁移 |
| 迁移成本 | 每张表升级一次 | 每个租户各升级一次 |
| 跨租户统计 | 通过授权的超管会话统一聚合 | 需跨库读取与汇总 |
| 运维成本 | 一个连接池和备份流程 | 随租户数增加的连接与备份流程 |

**结论：选择行级隔离。** 当前是课程规模的 3 个演示租户，库级隔离的物理优势不足以抵消迁移与运维开销。行级隔离的风险是漏加 `tenant_id`：本项目用 `app/db/tenant_hook.py` 中的 `do_orm_execute` 对 `TenantMixin` 的 ORM SELECT 统一注入 `tenant_id`，`before_flush` 守卫写入并禁止批量 ORM DML，缺少租户上下文时业务表访问失败关闭（fail-closed）。这大幅减少漏隔离风险，但**不能宣称彻底消除**：原生 SQL、engine 直连、未来不混 mixin 的模型仍是评审重点。

## 模型与索引契约

- 身份层 `Tenant / User / Role` 是受控白名单，不继承 `TenantMixin`；登录、用户名全局去重、租户管理需访问身份层。
- 业务层 `KnowledgeBase / Document / UsageRecord` **全部继承 `TenantMixin`**，每个实例必须有 `tenant_id`。
- 每个业务表显式声明 `(tenant_id, created_at)` 复合索引，供租户等值匹配 + 时间范围扫描（`ix_kb_tenant_created`、`ix_doc_tenant_created`、`ix_usage_tenant_created`）。ORM 模型定义同时作为 SQLite 开发期建表来源；MySQL 生产迁移需单独验证。
- `UsageRecord` 存储租户 ID、方法、路径、状态码、请求耗时与创建时间；`api_key_id` 为待接入字段。`/api/usage/summary` 与 `/api/usage/records` 都是 ORM 查询，自动隔离。

## 审计与已知绕过点

- `get_current_user` 从经签名验证的 JWT 读出租户，核对数据库中的用户所属租户，再将租户 ID 传给请求 Session；`Session.get` 的 identity map 命中仅适用于请求内已读出的对象。
- `require_super_admin` 实时核验平台角色后，在当前 Session 打开跨租户绕过；独立的 `seed` Session 显式声明维护级绕过。业务接口不得调用绕过 API。
- `app/api/v1/health.py` 的 `SELECT 1` 是**已登记的 Core SQL 豁免**，不读业务表。任何其他 raw SQL 或 engine 直连绕过必须走专项评审和租户条件审查；当前静态守护测试扫描业务路由。
- 复合索引在既有库上由 `create_all` 补建：需启动应用或显式执行迁移后才能确认索引已存在。不要在未备份生产库时直接运行迁移。
