# 多租户隔离验证报告（模块 B）

- 项目：智能问答 SaaS 平台
- 验证日期：2026-10-15
- 范围：**当前已实现的**知识库、文档、用量流水；API Key、知识块、账单导出模块尚不存在，不纳入通过数。
- 验证环境：Python 3.13.12 / SQLAlchemy 2.0.36 / FastAPI 0.115.0 / SQLite（临时独立库），不修改交付的 `qa.db`。
- 关键代码：`backend/app/db/tenant_hook.py`、`backend/app/models.py`、`backend/app/deps.py`、`backend/app/routers/usage.py`。

## 1. 方案与取舍

共享 schema 的业务表统一带 `tenant_id`，在 `do_orm_execute` 中对 ORM SELECT 自动注入 `with_loader_criteria(TenantMixin, ..., include_aliases=True)`；对象增删改由 `before_flush` 检查归属，租户上下文中的批量 ORM DML 被拒绝。详细取舍见 [数据库设计.md](数据库设计.md)。

不混 `TenantMixin` 的身份层白名单为 `Tenant / User / Role`；登录、注册和全局用户名查重使用这些表。新业务表若不继承 `TenantMixin` 就不会自动隔离，测试守护全体映射模型。

跨租户按 ID 访问统一返回 **404** 且与随机不存在 ID 的响应体完全一致；若返回 403，则攻击者可通过状态差异枚举其他租户存在的资源。同租户只读成员试图修改资源仍返回 403（角色权限不足）。

## 3. 实际测试方法

在 `smartqa-platform/backend` 目录执行：

```bash
python -m pytest tests/test_isolation.py tests/test_observability.py -q
# 本次：31 passed，0 failed（见 tests/reports/isolation_report.md）
```

pytest fixture 每例在临时 SQLite 建库，A 与 B 分别有租户管理员及各自 JWT；对攻击请求逐项与“不存在 ID”的响应做状态/JSON 完全相等断言，且对原始业务表回读证实没有误修改。用量测试先独立为 A 写入 `/A-ONLY-USAGE`，再核对 B 的汇总/明细与 A 的明细。另在隔离的启动库跑了真实 lifespan/seed，登录成功、A 读取 2 个知识库、用量汇总成功；随后通过本地端口 8765 运行原有越权脚本得到 27/27 拦截、0 泄露。`/health` 如实报告数据库和本地缓存 `up`、未配置的模型 `unconfigured`（503）。

## 4. 安全边界与未完成项

- ORM 钩子**不能拦截** `session.execute(text(...))` 等 Core SQL、`engine.connect()` 直连；健康检查 `SELECT 1` 是仅有的明确登记豁免（不含业务表）；业务路由静态测试阻止常见绕过写法。需要原生 SQL 时先走审查并强制带租户参数。
- `seed` 用独立 Session 显式声明维护绕过；业务表无上下文拒绝。`require_super_admin` 实时校验角色后才允许在请求 Session 的上下文管理器中临时启用跨租户绕过，请求结束自动复位，普通管理员不能启用。
- 已测试 SQLAlchemy `aliased()`/join/聚合以及业务对象写入；直接 Core 级访问与 DB 管理员账号属于架构外威胁面，需额外数据库权限控制。
- 缺失的 API Key、知识块、账单导出和配额/限流模块，**不得写成已通过验收**；后续模型/接口落地须继承 `TenantMixin`、加对应端到端越权用例并重新出报告。
- 当前 SQLite 开发库通过 `create_all` 自动建复合索引；MySQL 生产迁移和恢复脚本需在测试库再次验证。

## 5. 结论

**已实现资源范围内的租户隔离验收通过**：8/8 参数化接口攻击与现场脚本 27/27 项攻击均被拒绝，404 不泄露存在性，列表、用量与关联/别名查询被隔离。报告不覆盖尚未实现的功能；整份成员 B 任务书仍需等待 API Key、知识块、账单和真实模型服务的后续集成验收。
